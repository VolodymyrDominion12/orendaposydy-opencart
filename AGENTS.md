## 1. Золоті правила (порушувати не можна)

1. **Спершу специфікація.** Будь-яка фіча чи зміна поведінки йде через `specs/` (розділ 2).
2. **Ядро OpenCart не редагуємо.** Тільки OCMOD, події (`oc_event`), власні модулі й тема.
3. **Схема БД змінюється лише міграцією** в `db/migrations/` з `down`-файлом і перевіркою індексів (розділ 4).
4. **Кожен новий або змінений запит до БД проходить EXPLAIN**, а сторінка — профіль кількості запитів (розділ 5).
5. **PHP 7.3.** Жодних arrow functions, typed properties, `??=`, `match`, `?->`, named args, `str_contains` (розділ 3).
6. **Нічого не вважається готовим без перевірок** з розділу 6 і звіту про те, що саме перевірено.
7. **Секрети не комітяться і не виводяться в лог/чат:** `.env`, `config.php`, `admin/config.php`, паролі, токени.
8. **Прод не чіпаємо напряму.** Тільки `make deploy` (dry-run) → підтвердження людини → `make deploy-apply`.
9. **Мок-дані позначені й видаляються однією командою.** На прод не потрапляють (розділ 10).
10. **Мобільна версія — основна.** Кожна зміна вітрини проходить `make test-mobile` у бюджеті (розділ 8).
11. **Змінюй лише те, що просили.** Побачив іншу проблему — запиши в `specs/BACKLOG.md` або скажи, не виправляй мовчки.

## 2. Spec-Driven Development (SDD)

Повний процес і шаблони: `specs/README.md`. Коротко:

```
spec.md  →  plan.md  →  tasks.md  →  реалізація  →  verify  →  spec.status = Done
 ЩО і НАВІЩО   ЯК технічно   кроки з чекбоксами   код       make verify + приймання
```

- Одна фіча = тека `specs/NNN-slug/` (номер з `specs/BACKLOG.md`).
- **`spec.md`** — проблема, користувачі, сценарії, **критерії приймання** (Given/When/Then), поза межами, відкриті питання. Без технічних рішень.
- **`plan.md`** — файли, які чіпаємо, OCMOD/події, міграції, **запити та індекси**, ризики, як відкотити.
- **`tasks.md`** — малі кроки (≤ ~1 год кожен), у кожного — як перевірити.
- Реалізація йде **по tasks.md**, кожен виконаний крок відмічається `- [x]`.
- Розійшовся код зі специфікацією — **спершу правиш spec/plan**, потім код.
- Кожен критерій приймання має відповідну перевірку: smoke-URL, SQL-перевірку або ручний пункт у `tasks.md`.

**Без специфікації можна:** виправити опечатку, явний баг в одному файлі, оновити документацію.
Усе інше — через `specs/`. Статуси: `Draft → Approved → In progress → Done` (Approved ставить людина).

## 3. Код OpenCart

### Куди писати
| Що | Де |
|---|---|
| Правка поведінки ядра | OCMOD (`src/system/*.ocmod.xml` або модуль з `install.xml`), потім `make refresh-mods` |
| Реакція на дію (редирект, логування, доповнення даних) | Подія в `oc_event` + контролер `extension/kristal/...` |
| Новий функціонал (калькулятор, комплекти, редиректи) | Власний модуль `extension/module/kristal_*` (admin + catalog) |
| Вигляд | Тема `catalog/view/theme/kristal/` (twig, css, js); `sauco` не правимо |
| Тексти інтерфейсу | Мовні файли `language/uk-ua/...`, не хардкод у twig |

- **Спільна бібліотека `Kristal\*`** (`system/library/kristal/`, фіча 019) — не пиши свого, якщо є готове.
  Класи підвантажує автолоадер ядра (без `$this->load->library()`):
  | Потрібно | Клас |
  |---|---|
  | Контакти (телефони, месенджери, адреса, графік, соцмережі) | `\Kristal\Nap::get($this->registry)` — з кешем `kristal.nap`, 0 запитів |
  | Телефон: нормалізація, `tel:`, показ, маска | `\Kristal\Phone` |
  | Захист форми (honeypot + токен + time-trap + ліміт IP) | `\Kristal\Antispam::fromConfig(...)` + `\Kristal\Rate_limit`; тексти — `catalog/language/*/extension/module/kristal_core.php` |
  | Telegram | `\Kristal\Telegram` (не кидає винятків, токен у помилках — `***`) |
  | JSON-LD | `\Kristal\Jsonld::localBusiness()`, `render()` |
  | Лог без персональних даних | `new \Kristal\Log()` → `storage/logs/kristal.log` (не реєструй як `log` — це ядровий логер) |
  | Скинути кеш наших модулів | `\Kristal\Cache_key::flush($this->cache)` |
  Новий клас бібліотеки — з тестом у `tests/lib/` (`make test-lib`).
- Префікс усього нашого: **`kristal_`** (модулі, події, таблиці, налаштування, CSS-класи `k-`).
- Доступ до БД — лише `$this->db->query()` з **`DB_PREFIX`**; числа через `(int)`/`(float)`, рядки через `$this->db->escape()`.
- Повторні дані (меню, категорії, налаштування) кешуються `$this->cache->get/set` з ключем `kristal.*` і скидаються при зміні.
- Після змін у twig/OCMOD: `make clear-cache` / `make refresh-mods`.

### PHP 7.3 — заборонено
| Синтаксис | З якої версії |
|---|---|
| `fn($x) => ...`, typed properties, `??=`, `1_000` | 7.4 |
| `match`, `?->`, named arguments, union types, `str_contains/str_starts_with`, `static` return | 8.0 |
| enums, readonly, `never`, `new` в ініціалізаторах | 8.1 |

`make lint` перевіряє синтаксис реальним PHP 7.3 (прод), а не 7.4 з контейнера, і додатково PHP 8.3 (сумісність наперед).
Код, що працює на 7.3, але ламається на 8.x (`each()`, `create_function()`, фігурні дужки для індексу рядка, `count()` від не-масиву тощо), теж не пишемо.

### Twig 3
З 3.0.4.1 шаблони рендерить Twig 3.8. Не використовуємо прибрані конструкції: `{% spaceless %}`, тег `{% filter %}`,
`{% for … if … %}`, тест `sameas`, класи `Twig_*`. Замість них — `|spaceless`, `{% apply %}`, `|filter`, `same as`.

## 4. База даних і зміна схеми

Детально: `docs/agents/db-schema-checklist.md`.

- **Тільки міграції:** `db/migrations/NNNN_slug.up.sql` + `NNNN_slug.down.sql`, плейсхолдер `{{PREFIX}}`. Застосування — `make migrate`, відкат — `make migrate-down V=NNNN`.
- Міграція **ідемпотентна** (`IF NOT EXISTS`, `IF EXISTS`, перевірка через `information_schema`) і не ламає дані.
- Нові таблиці: `ENGINE=InnoDB`, `utf8mb4_general_ci`, первинний ключ обов'язковий, назва `{{PREFIX}}kristal_*`.
- Ядрові таблиці OpenCart змінюємо лише додаванням індексів або нових колонок з `DEFAULT` (ніколи не перейменовуємо й не видаляємо).
- **Після будь-якої зміни схеми обов'язково:**
  1. `make db-check` — без нових проблем (таблиці без PK, `*_id` без індексу, дубльовані індекси);
  2. `make db-schema-diff` — диф зрозумілий і збігається з міграцією; потім `make db-schema-snapshot` і комміт `db/schema.sql`;
  3. для кожного запиту, що користується новою таблицею/колонкою — `make db-explain`;
  4. `make migrate-down` + `make migrate` проходять без помилок (відкат перевірено).
- **Індекси:** на кожну колонку, яка стоїть у `WHERE`, `JOIN ... ON`, `ORDER BY` гарячих запитів. Складений індекс — колонки в порядку: рівність → діапазон → сортування. Не дублювати лівий префікс наявного індексу. Назви `idx_<колонки>`, унікальні `uq_<колонки>`.
- На прод міграція йде через phpMyAdmin: `make migrate-print V=NNNN` → `make deploy-sql`.

## 5. Оптимізація запитів

Детально: `docs/agents/query-performance.md`.

- **Жодних запитів у циклі** (N+1). Збираєш id → один запит з `IN (...)`.
- `SELECT` лише потрібних колонок; `LIMIT` на всіх списках; без `ORDER BY RAND()`; `LIKE 'x%'`, а не `'%x%'` на великих таблицях.
- Без функцій над індексованою колонкою в `WHERE` (`DATE(col) = ...` → діапазон).
- **`make db-explain SQL="..."`** для кожного нового/зміненого запиту: недопустимі `type=ALL` на таблицях > 1000 рядків, `Using filesort`/`Using temporary` на гарячих сторінках без пояснення в `plan.md`.
- **`make db-profile URL=/шлях`** до і після зміни для зачеплених сторінок. Бюджет (стартовий, уточнимо після першого заміру): головна ≤ 80, категорія ≤ 100, товар ≤ 80 запитів; найповільніший запит ≤ 50 мс. Зростання кількості запитів пропорційно кількості товарів = N+1, це блокер.
- Цифри «до/після» записуються в `tasks.md` фічі.

## 6. Тестування і Definition of Done

Детально: `docs/agents/testing.md`.

| Рівень | Команда | Коли |
|---|---|---|
| Синтаксис PHP 7.3 + 8.3 | `make lint` | кожна зміна PHP |
| Тести бібліотеки `Kristal\*` | `make test-lib` | кожна зміна `system/library/kristal/` |
| Аудит схеми | `make db-check`, `make db-schema-diff` | кожна міграція |
| План запиту | `make db-explain SQL=...` | кожен новий/змінений запит |
| Профіль сторінки | `make db-profile URL=...` | зміни, що зачіпають вітрину |
| Smoke вітрини | `make test-smoke` | перед кожним деплоєм і в кінці фічі |
| Мобільний аудит | `make test-mobile` (один раз `make mobile-setup`) | кожна зміна вітрини |
| Приймання | ручні пункти з `tasks.md` + реальний телефон | кінець фічі |
| Усе разом | `make verify` | перед «готово» |

**Готово (DoD), коли:** усі задачі в `tasks.md` відмічені; `make verify` зелений; критерії приймання перевірені й позначені; немає PHP Notice/Warning у `make logs-php`; профіль запитів і мобільний бюджет дотримані; spec/plan відповідають коду; у звіті перелічено, що саме запускалось і з яким результатом. «Мало б працювати» — не звіт.

Нові smoke-перевірки для фічі дописуються в `tests/smoke/urls.txt` і `tests/smoke/redirects.txt`.

## 7. SEO (на кожній публічній сторінці)

- Рівно **один `<h1>`**, логотип — не `h1`. Унікальні `title` (≤ 60 симв.) і `meta description` (≤ 160).
- `rel="canonical"`; фільтри/сортування/пагінація — canonical на базову сторінку; кошик, пошук, кабінет — `noindex`.
- ЧПУ-адреси без `index.php?route=`; ключові слова в `oc_seo_url` унікальні, транслітерація латиницею, `-` між словами.
- Змінив URL → запис у таблиці редиректів (301) + рядок у `tests/smoke/redirects.txt`.
- Мікророзмітка JSON-LD: `LocalBusiness`, `Product`/`Offer`, `BreadcrumbList`, `FAQPage` — лише з реальних даних сторінки.
- Зображення: `alt`, `width/height`, `loading="lazy"` (крім першого екрана), WebP.

## 8. Мобільна версія — основна

Детально: `docs/agents/mobile.md`. Клієнти шукають оренду з телефону й одразу дзвонять — мобільна версія проєктується першою, десктоп її розширює.

- **Бюджети** (`tests/mobile/budgets.json`, емуляція 360px + повільний 4G + CPU ×4): LCP ≤ 2.5 с, CLS ≤ 0.1, TBT ≤ 300 мс, вага ≤ 1200 КБ (JS ≤ 250, CSS ≤ 80, шрифти ≤ 120, зображення ≤ 700), ≤ 50 запитів.
- **Нуль** горизонтального скролу на 360px, тач-зон менших за 44×44, тексту дрібнішого за 12px (основний — 16px).
- Кожен `<img>`: `width`/`height`, WebP, `srcset`; нижче першого екрана — `loading="lazy"`, LCP-зображення — `fetchpriority="high"` без lazy.
- Нижня мобільна панель «Каталог · Дзвінок · Viber · Кошик»; телефон — `tel:`; поля форм — `type="tel"`, `autocomplete`, `inputmode`.
- Масштабування не забороняємо (`user-scalable=no` — заборонено).
- JS з `defer`, сторонні віджети й карти — відкладено; шрифти — лише кирилиця й потрібні накреслення, `font-display: swap`.
- `make test-mobile` — обов'язково для кожної зміни вітрини; перевищення бюджету = не готово. Плюс ручна перевірка на реальному телефоні для форм і кошика.

## 8a. Бренд і доступність

- Кольори, шрифти, відступи — **лише токени** з `docs/brandbook/tokens.css` (`var(--gold)`), без hex у компонентах.
- Темна тема основна; золото ≈ 10% площі, рубін ≤ 5%; текст на золоті — `--on-gold`; кути ≤ 4px.
- Контраст тексту ≥ 4.5:1, видимий фокус, `alt` у зображень, підписи полів.
- Без jQuery-плагінів «на всяк випадок»; кожен новий скрипт/шрифт — обґрунтування в `plan.md` (вплив на мобільний бюджет).

## 9. Безпека

- Вхідні дані: `(int)` для id, `escape()` для рядків, вивід у twig — через автоекранування (без `|raw` для даних користувача).
- Форми з записом (заявки, калькулятор) — CSRF-токен або перевірка `HTTP_REFERER` + honeypot/ліміт частоти.
- Адмін-маршрути перевіряють `$this->user->hasPermission('modify', ...)`.
- Не логувати персональні дані клієнтів (телефон, email) у файли логів.
- Тека `install/` на проді має бути видалена; `admin/` — перейменована (окрема задача з людиною).

---

## 10. Мок-дані

Поки клієнт не дав реальні ціни/фото/тексти, усе вигадане.
- Мок-товари: `sku` починається з **`MOCK-`**, `model` = `MOCK`; мок-категорії й сторінки — `meta_keyword` містить `mock`.
- Ціни, цифри «з 2013 року», «5000 позицій», відгуки — вигадані; у `spec.md` фічі є розділ «Мок-дані» зі списком, що замінити на реальне.
- Мок завантажується й видаляється міграцією (`make migrate` / `make migrate-down`), **ніколи** не деплоїться на прод: міграції з `mock` у назві `make migrate-print` відмовляється друкувати без `ALLOW_MOCK=1`.
- Фальшиві відгуки «від реальних людей» не публікуємо навіть локально в демо для клієнта — лише з позначкою «приклад».

## 11. Деплой

- Порядок: `make verify` → `make deploy` (dry-run) → показати людині список → `make deploy-apply` лише після «так».
- SQL на прод — тільки через `make deploy-sql` і phpMyAdmin, після бекапу бази.
- Ніколи не деплоїться: `config.php`, `admin/config.php`, `system/storage/`, `image/cache/`, `.htaccess`, `install/`, `*.sql` (захищено в `tools/lib.sh`).
- Після деплою — `make test-smoke BASE=https://orendaposydy.com`.

---

## 12. Git і звітність

- Гілки: `feature/NNN-slug`, `fix/короткий-опис`. Комміт: `NNN: що зроблено` (номер специфікації).
- Один комміт — одна логічна зміна; згенероване (`storage`, `image/cache`) не комітиться.
- Звіт агента в кінці роботи: що зроблено (файли), які команди перевірки запускались і результат, що лишилось/відкриті питання. Без переказу кожного кроку.

## 13. Коли зупинитися і спитати людину

- Незрозуміло, що саме вважати готовим (немає критеріїв приймання).
- Потрібно змінити ядро OpenCart, видалити дані, змінити URL з трафіком, щось на проді.
- Перевірка падає, і виправлення виходить за межі задачі.
- Потрібні реальні дані клієнта (ціни, умови, юридичні тексти) — не вигадувати поза мок-режимом.
