# Чек-лист: продуктивність запитів до БД

## Під час написання коду

- [ ] Немає запитів усередині `foreach`/`for` (N+1). Списки дочитуються одним запитом `WHERE id IN (...)`.
- [ ] `SELECT` перелічує потрібні колонки (не `*`) у нових запитах на великих таблицях.
- [ ] Є `LIMIT` для будь-якого списку, що виводиться користувачу; пагінація через `LIMIT offset, count` з `(int)`.
- [ ] У `WHERE` немає функцій над індексованою колонкою: `DATE(date_added) = '...'` → `date_added >= '... 00:00:00' AND date_added < '...'`.
- [ ] Немає `ORDER BY RAND()`; для «випадкових» товарів — вибірка id і перемішування в PHP або кеш.
- [ ] `LIKE '%текст%'` лише на малих таблицях або з обмеженням; пошук по каталогу — через ядровий `getProducts(filter_name)`.
- [ ] Типи в умові збігаються з типом колонки (`product_id = 5`, а не `'5'` для INT — інакше може не взяти індекс при порівнянні рядка з числом).
- [ ] Результати, що рідко змінюються (меню, дерево категорій, комплекти, налаштування модуля), кешуються `$this->cache` з ключем `kristal.*`; кеш скидається при збереженні в адмінці.
- [ ] Масові вставки — одним `INSERT ... VALUES (...), (...)` або пачками по 500.
- [ ] `COUNT(*)` для пагінації рахується тим самим `WHERE`, але без `ORDER BY` і `JOIN`, що не впливають на кількість.

## Перевірка

1. **EXPLAIN кожного нового/зміненого запиту**
   ```bash
   make db-explain SQL="SELECT p.product_id FROM {{PREFIX}}product p WHERE p.status = 1 ORDER BY p.sort_order LIMIT 20"
   make db-explain FILE=specs/003-.../queries.sql
   ```
   Скрипт підсвічує: `type=ALL` на таблиці > 1000 рядків, `Using filesort`, `Using temporary`, `key = NULL`.
   Прийнятно без пояснення: `const`, `eq_ref`, `ref`, `range`, `index` на малих таблицях.

2. **Профіль сторінки до і після**
   ```bash
   make db-profile URL=/mebli
   ```
   Показує кількість запитів, сумарний час, топ-10 найповільніших і топ-10 найчастіших (нормалізованих) запитів.
   Найчастіший запит з десятками повторів = N+1.

3. **Бюджет (стартовий, переглянути після першого заміру на `sauco`)**

   | Сторінка | Запитів | Найповільніший |
   |---|---|---|
   | Головна | ≤ 80 | ≤ 50 мс |
   | Категорія (20 товарів) | ≤ 100 | ≤ 50 мс |
   | Товар | ≤ 80 | ≤ 50 мс |
   | Кошик / оформлення | ≤ 80 | ≤ 50 мс |

   Перевищення — блокер для злиття, якщо в `plan.md` немає погодженого пояснення.

4. **Записати цифри** у `tasks.md` фічі: «/mebli: 74 → 71 запит, макс 12 мс».

## Типові пастки OpenCart 3

- Модулі на кшталт «Рекомендовані»/«Хіти» викликають `getProduct()` для кожного товару → N+1. Брати `getProducts()` з `filter_product_ids` або свій пакетний запит.
- `model_catalog_category->getCategories()` у меню на кожному рівні — кешувати дерево цілком.
- `oc_product_to_category`, `oc_product_to_store`, `oc_seo_url(query)`, `oc_seo_url(keyword)` — перевір індекси через `make db-check`; на старих збірках їх бракує.
- Таблиці ядра можуть бути MyISAM (табличні блокування на запис). Конвертацію в InnoDB робимо окремою міграцією за погодженням.
