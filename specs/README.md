# Spec-Driven Development у цьому проєкті

Кожна фіча спершу описується, потім планується, потім робиться. Так агент (і людина)
завжди знає, **що** вважати готовим, а перевірки виходять із критеріїв приймання, а не з голови.

## Структура

```
specs/
├── README.md            ← цей файл
├── BACKLOG.md           ← усі фічі з концепції, номери, статуси, порядок
├── _templates/
│   ├── spec.md          ← ЩО і НАВІЩО
│   ├── plan.md          ← ЯК (технічно)
│   └── tasks.md         ← КРОКИ з перевірками
└── 001-mock-catalog/
    ├── spec.md
    ├── plan.md
    └── tasks.md
```

## Цикл фічі

| Крок | Хто | Результат | Вихід із кроку |
|---|---|---|---|
| 1. Spec | агент пише, людина погоджує | `spec.md`: сценарії, критерії приймання Given/When/Then, поза межами, мок-дані, відкриті питання | статус `Approved` |
| 2. Plan | агент | `plan.md`: файли, OCMOD/події, міграції, запити + індекси, ризики, відкат | людина переглянула |
| 3. Tasks | агент | `tasks.md`: кроки ≤ ~1 год, у кожного «як перевірити» | — |
| 4. Реалізація | агент | код + відмічені `- [x]` | усі кроки виконано |
| 5. Verify | агент | `make verify` + розділ «Приймання» в `tasks.md` з результатами | DoD з `AGENTS.md` §6 |
| 6. Done | людина | статус `Done` у spec і `BACKLOG.md` | — |

## Правила

- **Spec не містить технічних рішень** (таблиці, класи) — лише поведінку, яку видно користувачу/адміну.
- **Критерій приймання = перевірка.** Якщо його неможливо перевірити — переписати.
- **Змінилась поведінка під час реалізації** → спершу правка `spec.md`/`plan.md`, потім код.
- **Одна фіча — одна гілка** `feature/NNN-slug`, комміти з префіксом `NNN:`.
- **Відкриті питання** не вирішуються мовчки: або мок з позначкою, або питання людині.
- Фіча, що змінює схему БД, обов'язково має в `plan.md` чек-лист із `docs/agents/db-schema-checklist.md`.
- Фіча, що додає/змінює запити, має в `plan.md` таблицю «запит → індекс → EXPLAIN-результат».
