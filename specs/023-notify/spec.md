## Проблема
Зараз у системі є застарілий сторонній модуль `notifications_in_telegram`:
1. Він хардкодить токен бота відкрито в БД і дампах (`oc_setting`).
2. Працює синхронно і без обробки збоїв (якщо Telegram API недоступний — замовлення може зависнути або впасти з PHP error).
3. Підтримує лише один чат, не вміє шле листи менеджеру і не має вебхуків для майбутньої CRM.
4. Не веде журналу відправок — неможливо перевірити, чи дійшло сповіщення про заявку/замовлення, або повторити відправку у разі збою мережі.
5. Викликається не подією ядра, а жорстко зашитим кодом у `checkout/order.php`.

## Мета і метрика
- Жодна заявка клієнта не губиться: час доставки сповіщення в Telegram ≤ 3 с, дублювання на email менеджера.
- Журнал спроб доставки (`oc_kristal_notify_log`) з можливістю повторної відправки невдалих повідомлень.
- Готовність до підключення будь-якої CRM через стандартизований JSON-вебхук з HMAC-підписом.
- Повна відмова від стороннього `notifications_in_telegram`.

## Користувачі та сценарії
- **Як** менеджер з оренди, **я хочу** отримувати миттєві сповіщення про нові замовлення та ліди в робочий Telegram-чат з усіма деталями (контакт, склад, дати, сума), **щоб** передзвонити клієнту за 5–15 хвилин.
- **Як** адміністратор, **я хочу** вказати кілька Telegram-чатів (або окремі чати для замовлень і для швидких лідів/дзвінків), **щоб** розділяти потік завдань між співробітниками.
- **Як** адміністратор, **я хочу** протестувати відправку кнопкою «Тест» прямо з адмінки, **щоб** переконатися у вірності налаштувань бота чи пошти без оформлення реального замовлення.
- **Як** інтегратор/розробник, **я хочу** увімкнути вебхук на зовнішню CRM (KeyCRM / SalesDrive) з HMAC-підписом, **щоб** заявки потрапляли в CRM автоматично.
- **Як** адміністратор, **я хочу** бачити історію відправок і помилок у журналі, **щоб** виявити збої мережі та повторити надсилання за потреби.

## Критерії приймання
- **AC-1. Telegram: надійне надсилання.** Given налаштовано коректний Bot Token та один або декілька `chat_id` (через кому чи з нового рядка), When надходить нове замовлення або лід, Then повідомлення відправляється в усі вказані чати за допомогою `\Kristal\Telegram`, спецсимволи екрануються (HTML parse_mode), у тексті є пряме посилання на замовлення/лід в адмінці.
- **AC-2. Telegram: відмовостійкість.** Given Telegram API недоступний (таймаут, блокування, помилка мережі 5xx/4xx), When модуль намагається відправити сповіщення, Then клієнт не бачить помилки, замовлення успішно зберігається в базі, помилка записується в `oc_kristal_notify_log` зі статусом `failed`, а токен бота не витікає в лог.
- **AC-3. Email сповіщення.** Given увімкнено канал Email та вказано адресу отримувача, When створюється замовлення або лід, Then через поштовий сервіс ядра надсилається лист з інформацією про подію та реквізитами клієнта.
- **AC-4. Вебхук CRM.** Given увімкнено канал Webhook, вказано URL та секретний ключ, When виникає подія (нове замовлення або лід), Then на цей URL надсилається HTTP POST запит із заголовком `Content-Type: application/json` та `X-Kristal-Signature: sha256=<hmac>` (HMAC-SHA256 від тіла запиту), а тіло містить JSON з типом події, entity_id, даними клієнта і замовлення/ліда.
- **AC-5. Журнал сповіщень.** Then кожна спроба відправки (в кожен канал окремо) записується в таблицю `oc_kristal_notify_log` з полями: канал, тип події, id сутності, адресат, статус (`sent`/`failed`), час виконання, текст помилки (якщо є) та короткий анонімізований опис.
- **AC-6. Адмінка: налаштування та тести.** Given адміністратор відкриває «Модулі → Крістал: сповіщення», Then він бачить перемикачі статусів для кожного каналу (Telegram, Email, Webhook), поля токена і чатів, кнопку «Надіслати тестове сповіщення» для кожного каналу із негайним відображенням результату (успіх/код помилки).
- **AC-7. Адмінка: перегляд журналу та повтор.** Given в адмінці є вкладка «Журнал», Then показуються останні 50 записів із фільтрами за статусом (`failed`, `sent`) і каналом. Для записів зі статусом `failed` доступна дія «Повторити», яка робить повторну спробу і оновлює статус запису.
- **AC-8. Безпека та конфіденційність.** Then у журналі `oc_kristal_notify_log` та системних логах `storage/logs` номери телефонів та email клієнтів маскуються (наприклад `+380 67 *** ** 89`), згідно з `AGENTS.md` §0 і §9. Токен Telegram бота в інтерфейсі адмінки частково маскується.
- **AC-9. Події OpenCart.** Then реакція на замовлення підключається через ядрову подію OpenCart `model/checkout/order/addOrderHistory/after` (або `order/add/after`), без редагування файлів ядра.
- **AC-10. Заміна та міграція старої конфігурації.** Given у системі є налаштування старого модуля `notifications_in_telegram`, When адміністратор відкриває новий модуль або запускає установку, Then модуль пропонує (або автоматично переносить) Bot Token та Chat ID із `module_notifications_in_telegram_*`, після чого старий модуль вимикається.

## Нефункціональні вимоги
- **Швидкість:** час обробки сповіщення не блокує користувача (таймаут з'єднання до Telegram/вебхука ≤ 3 с, загальний таймаут ≤ 5 с).
- **Синтаксис:** сумісність з PHP 7.3 і 8.3 (перевірка `make lint`).
- **Без сторонніх бібліотек:** лише curl ядра PHP та бібліотека `\Kristal\Telegram`.

## Поза межами
- Двосторонній чат-бот для клієнтів (поки що це лише односторонні сповіщення для адміністрації).
- Готові специфічні API-клієнти окремих CRM (інтеграція стандартизована через generic Webhook).

## Мок-дані
- Тестовий токен бота та тестовий chat_id для перевірок (за замовчуванням вимкнені або вказуються в `.env`/конфігурації).
